# leaf 작성 가이드 (`update <chapter-id>` 절차)

`update <chapter-id>` 모드가 따르는 표준 절차. 어떤 도메인·프로젝트에서도 동일하게 적용된다.

---

## 0. 출처 발견 (update 시작 시 필수)

`update <chapter-id>` 호출 즉시 다음 절차를 수행한다.

1. `.claude/docs/source/` 디렉토리 존재 확인.
2. 디렉토리 내 모든 .md 파일을 **Read 도구로 전체 스캔**.
3. 각 파일의 헤딩(`^## `, `^### `, `^#### `)을 anchor 인덱스로 정리.
4. 파일·anchor 인덱스 요약을 사용자에게 보고.

발견 실패 시:
- 디렉토리 없음 → `create` 미실행 가능성. 사용자에게 보고.
- 디렉토리 비어 있음 → 사용자에게 자료 복사 요청 후 응답 대기.
- .md 외 형식만 있음 → 사용자에게 .md 변환 또는 백지 작성 여부 확인.

---

## 1. leaf 1개당 산출물 구조

### 1-1. Frontmatter (통일 표준)

`create` 시 복사된 leaf 파일이 이미 표준 frontmatter(3 키 고정: `file`/`title`/`last_updated`) + H1 + 출처 인용 블록 + 절 골격을 갖고 있다. `update`는 본 구조를 유지하면서 본문 절을 채운다. 추출 단계의 원본 anchor는 frontmatter가 아닌 **본문 H1 직후 출처 인용 블록**에 배치.

**상태 키 금지**: 진척 상태(`draft` / `review` / `confirm`)는 `docs/INDEX.md` 인덱스 표 1곳에서만 관리한다. frontmatter 에 `status` 키를 추가하지 않는다 — 이중 진실 회피.

### 1-2. 본문 (5~7개 절, 1 page 분량)

| 위치 | 내용 |
|------|------|
| H1 | `# {n-n}. {arc42 leaf 영문명} ({한국어 명칭})` |
| 인용 블록 | 본 leaf의 **범위와 비범위** 한 문장 정의. "이 문서는 X를 다루며, Y는 다루지 않는다." |
| 본문 절 | 5~7개 H2 절. 각 절은 **1 표 또는 짧은 문단**으로 자기완결. |
| 위임 표(끝) | "더 알고 싶다면" 표. 본문에서 의도적으로 다루지 않은 항목과 매핑되는 다른 leaf/챕터 anchor 명시. |

### 1-3. 절 헤딩 번호 규칙

- H2 = `## {n-n-1}.`, `## {n-n-2}.` ...
- H3 = `### {n-n-n-1}.` ...
- 본문 절 번호는 leaf 번호를 prefix로 부여하여 다른 leaf와 충돌 회피.

---

## 2. 작성 전 의사결정 (사용자 승인 대기)

`update` 호출 → source 스캔 → 본문 작성 사이에 다음을 사용자에게 보고하고 승인을 받는다.

| 항목 | 보고 형식 |
|------|----------|
| **A. 절 후보** | 4~7개 H2 절 제목 + 각 절 출처 anchor + 한 줄 요약 |
| **B. 위임 대상** | 본 leaf에서 **의도적으로 빼는 항목** + 그것이 가야 할 다른 leaf |
| **C. frontmatter** | 채택할 frontmatter 전문(file·title·template·source 후보) |
| **D. 결정 필요 사항** | 표현 방식 선택지, 강조 우선순위 등 |

사용자가 (A)~(D) 모두에 대해 명시 승인 또는 수정 요청을 한 후에야 본문 작성에 착수.

---

## 3. 작성 후 처리 (`update` 완료 직후)

1. 본문 파일 저장.
2. `.claude/docs/INDEX.md` 인덱스 표에서 해당 leaf 행의 상태를 `draft`(또는 기존) → `review`로 자동 갱신.
3. 사용자에게 작성 완료 + 검토 요청 메시지 전달.

→ 이 시점에서 LLM은 더 이상 상태를 변경하지 않는다. 사용자가 검토 후 `confirm <chapter-id>`를 명시 호출해야 `confirm` 상태로 전이.

## 5. 위임 표 작성 규칙

본문 끝의 "더 알고 싶다면" 표는 **본 leaf와 다른 leaf의 경계 명시 도구**. 다음을 포함한다.

- 본문에서 의도적으로 빼낸 항목 → 어디로 갔는지 정확한 leaf 경로
- 본문에서 짧게 언급만 한 항목 → 상세 leaf 경로
- 본문이 결정하지 않은 항목 → 결정이 기록될 leaf 경로 (보통 ADR `9_*` 또는 `11_*`)

위임 표는 **leaf 간 중복 제거의 핵심 메커니즘**. 같은 정보가 여러 leaf에 등장하지 않게 보장.

---

## 6. 검증 (작성 완료 후)

1. **3분 통독 가능 여부**: leaf를 처음 펼친 사람이 3분 내 핵심 파악되는지.
2. **anchor 정확성**: source 필드의 원본 anchor가 실제 존재하는지 grep으로 확인.
3. **위임 매핑 일관성**: 위임 표의 경로가 `docs/INDEX.md` 인덱스와 어긋나지 않는지.
4. **다른 leaf 침범 금지**: 다른 leaf 영역의 상세 정보가 본문에 새어 나오지 않았는지.
5. **frontmatter 표준 일치**: 3 키(`file`/`title`/`last_updated`)만 채워졌는지.
6. **README 진척 표 동기화**: 해당 챕터가 `review` 상태로 갱신되었는지.

---

## 7. `update` 재호출 (재작성)

같은 챕터에 대해 `update`를 다시 호출하면:
- 본문이 다시 작성됨 (사용자 승인 후).
- 진척 상태가 다시 `review`로 설정됨 (`confirm` 상태였더라도 `review`로 되돌림).
- 사용자에게 "재검토 필요" 메시지 전달.

이 동작은 의도적이다 — 변경된 본문은 사용자 재검토를 거쳐 다시 `confirm` 받아야 함.

---

## 8. 출처 섹션 라이프사이클

본문 H1 직후의 `> 출처` 인용 블록은 **추출 단계 한정**. 라이프사이클:

1. **삽입**: `update <chapter-id>` 시 자동 삽입.
2. **검증**: `grep -rE "^> .*docs/source/" docs/architecture/`로 누락·중복 확인.
3. **추출 완료**: 사용자 결정 시점에 git tag(예: `extraction-baseline-YYYY-MM-DD`) 부착 → 모든 leaf의 출처 섹션 일괄 제거.
4. **이후**: 과거 anchor는 git history(blame/log/tag)로 추적.
