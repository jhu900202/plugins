## 핵심 인식

현재 `leaf-spec.md` §0 은 .md 만 가정하고, 비-md 는 "변환 또는 백지 작성"으로 외부화. source/ 에 다양한 파일이 들어오는 시나리오를 진지하게 다루려면 새 설계가 필요하다.

## 다양한 파일 타입과 Read 도구의 대응 가능성

**스크립트 처리 확정 (구현 우선순위 순)**
| 확장자 | 사용 맥락 | 라이브러리 | 구현 난이도 |
|--------|----------|-----------|------------|
| `.pdf` | 공문·계약서·보고서 | pdfplumber | 낮음 |
| `.xlsx` | 기획서·데이터·양식 | openpyxl / pandas | 낮음 |
| `.docx` | 제안서·매뉴얼 | python-docx | 낮음 |
| `.pptx` | 발표자료 | python-pptx | 낮음 |
| `.csv` `.json` `.yaml` `.xml` | 데이터·설정·API 명세 | 내장 모듈 | 매우 낮음 |
| `.txt` `.md` `.html` | 텍스트 직접 처리 | Read 도구 | 없음 |

**수동 처리 (스크립트 불가)**
| 확장자 | 사유 |
|--------|------|
| `.hwp` `.hwpx` | pyhwp 구버전만 지원·hwpx 미지원 → 사용자가 PDF/docx로 사전 변환 요청 |
| `.png` `.jpg` | OCR 정확도 불보장 → 수동 기술 |
| `.psd` `.ai` `.fig` | 디자인 원본 파일 |

## 설계 옵션 3가지

### A. 사용자 관리 카탈로그 (`source/_catalog.md`) — 독립성·단순성 우선

- source/ 에 어떤 파일이든 둘 수 있음
- 사용자가 `source/_catalog.md` 를 직접 작성·유지 — 각 파일에 대해 (1) 경로 (2) 1~2 문장 요약 (3) 핵심 토픽·헤딩
- `update` 는 `_catalog.md` 를 우선 읽고, 거기에 명시된 자료를 따라 필요한 파일을 선택적으로 추가 Read
- 비-md 파일의 내용 요약은 카탈로그 안에 사용자가 이미 정제해 둔 형태

**Pro**: arc42 가 마크다운 도메인을 벗어나지 않음. Office·바이너리 처리 책임을 사용자에게 외부화. 가장 보편적·간단.
**Con**: 사용자 수작업 필요. 카탈로그 갱신 부담.

### B. 새 커맨드 `/arc42-source-prep` (또는 `/arc42-prep`)

- 사용자가 source/ 에 파일을 넣고 `/arc42-prep` 실행
- 커맨드가 각 파일을 Read 도구로 읽어 (Office 등 못 읽는 건 보고) 자동으로 `_catalog.md` 생성
- 이후 `/arc42-update` 가 카탈로그를 사용

**Pro**: 자동화. 사용자는 파일만 넣으면 됨.
**Con**: 새 커맨드 추가. arc42 가 파일 형식 처리에 책임 짐 (장기적으로 새 형식 추가 시 유지보수 부담). Office 등은 어차피 사용자 변환 필요 — 자동화의 한계.

### C. update 통합 (사전 단계 없음)

- update 가 step 0 으로 source/ 의 모든 파일 타입을 직접 처리
- 매 update 호출마다 PDF·이미지 재추출 (캐시 없음)

**Pro**: 단일 명령.
**Con**: update 가 비대해짐. 매 호출마다 무거움. 파일 형식 추가 시 update 수정.

## 권장 — A

이유:

1. **arc42 의 도메인 경계 유지** — arc42 는 "아키텍처 문서 작성" 도구이지 "파일 추출 도구" 가 아님. 추출은 사용자 책임으로 외부화하는 것이 책무 분리에 부합.
2. **독립성** — Office·바이너리 처리는 어차피 외부 도구(예: pandoc, pdftotext) 또는 사용자 수작업이 개입해야 함. 이 책임을 arc42 가 떠안으면 유지보수 영역이 무한 확장.
3. **유연성** — 사용자가 자료의 "맥락·핵심"을 직접 요약하므로 추출 품질이 모델의 자동 추출보다 일반적으로 우수.
4. **확장 계획 없음** 방침과 일치 — 새 커맨드(B) 미추가.

## source 처리 파이프라인 커맨드 설계 (확정)

단순 카탈로그 수작업(A안) 대신, source/ 처리를 4개 커맨드로 분리하는 파이프라인 구조로 확정한다. 각 커맨드는 독립 실행 가능하며, 앞 단계 산출물을 다음 단계가 입력으로 소비한다.

### 커맨드 체계 요약

| 커맨드 | 역할 | 주요 산출물 |
|---|---|---|
| `arc42-source-list` | source/ 파일 목록 리스트업 | `_file-list.md` 생성 |
| `arc42-source-convert` | 스크립트 기반 md 변환 | `_converted/*.converted.md` 생성, `_file-list.md` 상태 갱신 |
| `arc42-source-fragment` | 조건/요구사항 문장 단위 파편화 | `_fragments/**/*.md` + `_fragment-list.md` 생성 |
| `arc42-source-verify` | 파편화 완전성 검증 | `_verify/*.verify.md` + `_verify-report.md` 생성, `_fragment-list.md` 검증 상태 갱신 |

### 파편화 단위 확정

**조건/요구사항 문장 1개 = 파편 1개**. 예시 수준: "OO 기능 입력 텍스트는 400자로 제한한다". 파편이 50줄을 초과하면 강제 분할한다. 맥락 없이 단독으로 이해 불가능한 파편은 상위 문맥을 포함한 뒤 `context-merged: true` 로 표기한다.

### 검증 보고서 형식

`_verify-report.md` 는 정형화된 표가 아닌 **비정형 보고서**다. 누락·미처리된 원문 문장을 그대로 나열하는 방식으로 작성하며, 별도 집계 컬럼이나 통계 테이블을 두지 않는다.

```
## 0. 출처 발견 (update 시작 시 필수)

`update <chapter-id>` 호출 즉시 다음 절차를 수행한다.

1. `.claude/docs/source/` 디렉토리 존재 확인.
2. **`source/_catalog.md` 존재 확인 (권장 진입점).**
   - 있으면: 카탈로그를 Read 하고, 카탈로그가 가리키는 자료 파일들을 선택적으로 추가 Read.
   - 없으면: 디렉토리 내 모든 .md 파일을 Read 도구로 전체 스캔 (구버전 동작 호환).
3. 각 파일에서 헤딩 줄(`^## `, `^### `, `^#### `)을 추출하여 "파일명 → 헤딩 목록" 형식의 anchor 인덱스 생성.
4. 인덱스를 표 형태로 사용자에게 보고.

발견 실패 시:
- 디렉토리 없음 → `create` 미실행 가능성. 사용자에게 보고.
- 디렉토리 비어 있음 → 사용자에게 자료 복사 또는 백지 작성 여부 확인.
- 비-md 파일이 카탈로그 없이 존재 → 사용자에게 `_catalog.md` 작성 또는 .md 변환을 안내.
```
